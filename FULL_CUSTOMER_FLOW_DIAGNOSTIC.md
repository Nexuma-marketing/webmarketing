# Property Owner Flow (step-by-step table/function list)

1. **Account/person form — `src/app/(auth)/register/page.tsx`.** The Property Owner and Investor Owner share the `propietario` registration role; the UI label is “Property Owner / Investor.” `supabase.auth.signUp()` creates the Auth account (an Auth API operation whose underlying destination is `auth.users`, not a direct client table query), then `auth.getUser()` validates the session. The `auth.users` insert fires `public.handle_new_user()`, a `SECURITY DEFINER` trigger function defined in the migrations, which performs `INSERT` into `public.profiles`. The client also calls `logConsents()` in `src/lib/consent-log.ts`, which performs `INSERT` into `consent_logs` for Terms and Privacy. `profiles` and `consent_logs` are covered by v40; `auth.users` and `public.handle_new_user()` were not changed by v38-v40. The trigger does not require an `authenticated` function grant because it runs from the Auth insert, and its checked-in definition does not contain an admin-policy subquery.

2. **Role redirect — `src/app/(auth)/register/page.tsx`.** The metadata role is read from the authenticated user object, not from a public table, and the browser is sent to `/forms/propietario`. There is no separate registration route for investors.

3. **Owner/property form metadata — `src/app/forms/propietario/page.tsx` through `src/lib/form-meta.ts`.** `forms_dynamic` is queried with `SELECT id` for slug `owner_property`; `form_questions` is queried with `SELECT` for that form’s field definitions. Both tables are covered by v40 with authenticated `SELECT`, and v40 replaces their direct `profiles` staff checks with `public.is_forms_admin_or_marketing()`.

4. **Owner form submission — `src/app/forms/propietario/page.tsx`.** The page performs `INSERT` into `discovery_briefs`; `INSERT ... SELECT ... single()` into `properties`; file `UPLOAD` and public-URL resolution against Supabase Storage bucket `property-images` (backed by `storage.objects`); and `INSERT` into the relational `property_images` table. It calls `logConsents()`, which performs `INSERT` into `consent_logs`. `discovery_briefs` is covered by v38 (safe admin helper) and v39 (`SELECT/INSERT/UPDATE` grants). `properties`, `property_images`, and `consent_logs` are covered by v40. `storage.objects` was not covered by v38-v40; checked-in storage RLS has authenticated `INSERT`, public `SELECT`, and path-based owner `DELETE`, but current table-level grants cannot be confirmed without querying the database.

5. **Owner notification — `src/app/api/owner-submit-email/route.ts`.** The authenticated route performs `SELECT` on `profiles`; no database write or RPC occurs. `profiles` is covered by v40.

6. **Owner profiling/activation — `src/app/api/profiling/route.ts` and `src/lib/profiling.ts` (`profileOwner`).** Operations are `SELECT` on `properties`, `SELECT` on `profiles`, repeated `UPDATE` on owned `properties`, and `UPDATE` on the user’s `profiles` row. The updates fire `public.update_updated_at()` on `properties` and `profiles`. Both tables are covered by v40, and their admin checks use `public.is_customer_data_admin()`. `public.update_updated_at()` was not changed by v38-v40; it is a trigger function, not a client RPC, and contains no admin lookup.

7. **Lead creation — `src/app/api/leads/route.ts`.** After session validation, the endpoint uses the service-role client to `SELECT` `profiles`, `SELECT` `leads` for deduplication, and `INSERT` `leads`. `profiles` is covered by v40. `leads` is not covered by v38-v40, but these operations do not use the customer’s `authenticated` database role; they use `service_role`. The checked-in admin policy on `leads` still uses the old direct `profiles` subquery, while its service-role insert policy does not.

8. **Final redirect and owner dashboard — `src/app/forms/propietario/page.tsx`, `src/app/(dashboard)/layout.tsx`, and `src/app/(dashboard)/dashboard/properties/page.tsx`.** The form redirects to `/dashboard/properties`. The dashboard layout performs `SELECT` on `profiles` and `SELECT` on `site_content`. The properties page performs `SELECT` on `profiles`, `properties`, and `property_images`. The first three customer-data tables are covered by v40. `site_content` is not covered by v38-v40; no authenticated table grant is present in the checked-in migrations, its public-read RLS policy allows `SELECT`, and its admin policy uses the old recursive `profiles` subquery.

# Tenant Flow (step-by-step table/function list)

1. **Account/person form — `src/app/(auth)/register/page.tsx`.** `auth.signUp()` creates the Auth account, the `auth.users` insert invokes `public.handle_new_user()`, and that function performs `INSERT` into `profiles`. `auth.getUser()` validates the session. `logConsents()` performs `INSERT` into `consent_logs`. `profiles` and `consent_logs` are covered by v40; the Auth table and trigger function are not part of v38-v40, with the same trigger/function observations described in the Property Owner flow.

2. **Role redirect — `src/app/(auth)/register/page.tsx`.** The metadata role `inquilino` sends the browser to `/forms/inquilino`; no public table is queried for this routing decision.

3. **Tenant-form metadata — `src/app/forms/inquilino/page.tsx` through `src/lib/form-meta.ts`.** The code performs `SELECT` on `forms_dynamic` for slug `tenant_preferences`, followed by `SELECT` on `form_questions`. Both tables and their non-recursive staff checks are covered by v40.

4. **Tenant-preferences form — `src/app/forms/inquilino/page.tsx`.** The page first performs `SELECT id` on `tenant_preferences`, then either `UPDATE` of the existing own row or `INSERT` of a new own row. `logConsents()` performs `INSERT` into `consent_logs`. `tenant_preferences` and `consent_logs` are covered by v40. An `UPDATE` to `tenant_preferences` fires `public.update_updated_at()`, which is an existing trigger function not changed by v38-v40.

5. **Tenant profiling/activation and matching — `src/app/api/profiling/route.ts` and `src/lib/profiling.ts`.** `profileTenant()` performs `SELECT` on `tenant_preferences`, `SELECT` on `matching_rules`, `UPDATE` on `tenant_preferences`, `SELECT` on `profiles`, and `UPDATE` on `profiles`. It then calls `matchPropertiesForTenant()`, which performs `SELECT` on `tenant_preferences`, filtered `SELECT` on `properties` with an embedded `profiles` relationship, and `SELECT` on `property_images`. `tenant_preferences`, `profiles`, `properties`, and `property_images` are covered by v40. `matching_rules` is not covered by v38-v40: the checked-in RLS includes an authenticated `SELECT` policy but no checked-in authenticated table-level `SELECT` grant, and its admin/marketing policy uses the old direct `profiles` subquery. The table’s live grant state is unverified because the database was not queried.

6. **Lead and email side effects — `src/app/api/leads/route.ts` and `src/app/api/tenant-submit-email/route.ts`.** The lead route uses `service_role` for `SELECT profiles`, `SELECT leads`, and `INSERT leads`. The email route uses the customer session for `SELECT profiles` and makes no database write. `profiles` is covered by v40; `leads` is not, but the creation path is service-role based. Its old recursive admin policy remains as described above.

7. **Dashboard redirect — `src/app/forms/inquilino/page.tsx`, `src/app/(dashboard)/layout.tsx`, and `src/app/(dashboard)/dashboard/page.tsx`.** The form redirects to `/dashboard`. The layout performs `SELECT` on `profiles` and `site_content`. The dashboard page performs `SELECT` on `profiles`, invokes `matchPropertiesForTenant()` (therefore `SELECT tenant_preferences`, `properties` plus joined `profiles`, and `property_images`), then performs count-style `SELECT` on `leads` and `services`. Covered tables are `profiles`, `tenant_preferences`, `properties`, and `property_images`. `site_content`, `leads`, and `services` are not covered by v38-v40. No authenticated table grants for those three appear in checked-in migrations. `site_content` and `services` have public-read RLS policies but old recursive admin policies. `leads` has no customer-own read policy at all and has an old recursive admin policy, so the dashboard lead count cannot be authorized for a normal tenant by the checked-in RLS even if a base grant existed.

# Investor Owner Flow (step-by-step table/function list)

1. **Account/person form — `src/app/(auth)/register/page.tsx`.** There is no distinct Investor role in the initial role selector: Investor Owner enters through the same `propietario` choice as Property Owner. The database path is `auth.signUp()` → underlying `auth.users` insert → `public.handle_new_user()` → `INSERT profiles`, plus `INSERT consent_logs` through `logConsents()`. Coverage is identical to the Property Owner account step.

2. **Investor selection inside owner form — `src/app/forms/propietario/page.tsx`.** After `/forms/propietario`, the user chooses `user_type === "investor"`. Form metadata is loaded with `SELECT` from `forms_dynamic` and `form_questions` using slug `owner_property`; both are covered by v40.

3. **Investor portfolio submission — `src/app/forms/propietario/page.tsx`.** The shared owner form performs `INSERT discovery_briefs`; loops over the portfolio and performs one `INSERT ... SELECT ... single()` into `properties` per property; uploads files to Storage bucket `property-images`/`storage.objects`; and performs `INSERT property_images` for each uploaded image. It also performs `INSERT consent_logs`. The relational tables are covered by v38-v40. `storage.objects` is not covered and its live table grants are unverified; checked-in storage policies are described in the Property Owner flow.

4. **Notification, activation, and lead creation.** `src/app/api/owner-submit-email/route.ts` performs `SELECT profiles`. `src/app/api/profiling/route.ts` and `src/lib/profiling.ts` perform `SELECT properties`, `SELECT profiles`, repeated `UPDATE properties`, and `UPDATE profiles`; these updates invoke `public.update_updated_at()`. `src/app/api/leads/route.ts` uses `service_role` for `SELECT profiles`, `SELECT leads`, and `INSERT leads`. The customer-data tables are covered by v40; `leads` and the trigger function are not, with the same qualifications described above.

5. **Final redirect and dashboard — shared owner files.** The browser is redirected to `/dashboard/properties`; the layout performs `SELECT profiles` and `SELECT site_content`, and the properties page performs `SELECT profiles`, `properties`, and `property_images`. The Investor distinction is read from `profiles.role === "inversionista"`. The customer-data tables are covered by v40. `site_content` is not covered, has no checked-in authenticated table grant, and retains an old recursive admin policy.

# Company/PYME Flow — Path A (step-by-step table/function list)

1. **Account/person form — `src/app/(auth)/register/page.tsx`.** The `pymes` choice follows `auth.signUp()` → underlying `auth.users` insert → `public.handle_new_user()` → `INSERT profiles`; `logConsents()` performs `INSERT consent_logs`; and the browser is routed to `/forms/pymes`. `profiles` and `consent_logs` are covered by v40; the Auth table/function observations are the same as above.

2. **Assessment selector and diagnosis metadata — `src/app/forms/pymes/page.tsx` and `src/lib/form-meta.ts`.** Path A is the **Sales Leak Diagnosis** (`formType = "diagnosis"`). The hook performs `SELECT forms_dynamic` for slug `pymes_diagnosis`, then `SELECT form_questions`. Both tables are covered by v40.

3. **Diagnosis submission — `src/app/forms/pymes/page.tsx`.** The page performs `INSERT ... SELECT id ... single()` on `pymes_diagnosis`, then calls `/api/leads` and `/api/pymes-result-email`. `pymes_diagnosis` is covered by v40. Its insert does not invoke the update timestamp trigger because that trigger is `BEFORE UPDATE`, not insert.

4. **Lead and result-email routes — `src/app/api/leads/route.ts` and `src/app/api/pymes-result-email/route.ts`.** The lead route uses `service_role` for `SELECT profiles`, `SELECT leads`, and `INSERT leads`. The result-email route uses the authenticated client for `SELECT pymes_diagnosis` and `SELECT profiles`; it makes no database write. The two customer tables are covered by v40; `leads` is not covered, but this creation path is service-role based.

5. **Results step — `src/app/results/pymes/[id]/page.tsx`.** The form redirects here, not directly to Dashboard. The page performs `SELECT` on the user’s `pymes_diagnosis`, then attempts `SELECT id` from `pymes_plans` with a `user_id = current user` filter. Both tables are covered by v40 for `SELECT`. However, checked-in schema migrations define `pymes_plans` as a catalog without a `user_id` column; this query/schema mismatch requires human review. The results page offers links to `/dashboard/services`, not a “complete registration” database mutation.

6. **Dashboard/services destination — `src/app/(dashboard)/dashboard/services/page.tsx`.** The email and results page lead to `/dashboard/services`; the shared layout performs authenticated `SELECT profiles` and `SELECT site_content`. For a PYME, the services page performs authenticated `SELECT profiles`, latest `pymes_diagnosis`, active matching `pymes_plans`, active `services`, own `service_recommendations` with a joined `services` row, and readable plan-feature rows from `app_config`. Separately, a server-side service-role client performs `SELECT app_config`, `SELECT services`, and count-style `SELECT payments` for the Founders counter. `profiles`, `pymes_diagnosis`, `pymes_plans`, and `service_recommendations` are covered by v40. `site_content`, `services`, and `app_config` are not; their authenticated table grants are not present in checked-in migrations. Their customer/public read policies exist, but their staff/admin policies retain direct `profiles` subqueries. `payments` is also not covered, but this render-time read uses `service_role`, not the customer’s authenticated role.

# Company/PYME Flow — Path B (step-by-step table/function list)

1. **Account/person form and route — shared PYME registration files.** The database path is the same as Path A: Auth signup, `public.handle_new_user()` inserting `profiles`, `logConsents()` inserting `consent_logs`, then `/forms/pymes`.

2. **Assessment selector and acquisition metadata — `src/app/forms/pymes/page.tsx` and `src/lib/form-meta.ts`.** Path B is **Client Acquisition** (`formType = "captacion"`). The hook performs `SELECT forms_dynamic` for slug `business_acquisition`, then `SELECT form_questions`. Both are covered by v40.

3. **Client Acquisition submission — `src/app/forms/pymes/page.tsx`.** The page performs `INSERT` into `pymes_captacion`, calls `/api/leads`, and calls `/api/pymes-captacion-email`. `pymes_captacion` is covered by v40.

4. **Lead and email routes — `src/app/api/leads/route.ts` and `src/app/api/pymes-captacion-email/route.ts`.** The lead route uses `service_role` for `SELECT profiles`, `SELECT leads`, and `INSERT leads`. The email route uses the authenticated client for `SELECT profiles` and performs no database write. `profiles` is covered; `leads` is not, but its operations here use the service role.

The customer must click **Go to Dashboard**, which routes to `/dashboard`. The layout then performs `SELECT profiles` and `SELECT site_content`; the dashboard page performs `SELECT profiles`, latest `pymes_diagnosis`, count-style `SELECT leads`, and count-style `SELECT services`. `profiles` and `pymes_diagnosis` are covered by v40, although Path B does not create a diagnosis row. `site_content`, `leads`, and `services` are not covered. The checked-in grant/policy limitations for those tables are the same as in the Tenant dashboard step.

# Tables/Functions Already Fixed (v38-v40) — confirm still correct

- **v38:** `discovery_briefs` admin policy calls `public.is_discovery_briefs_admin()`, a `SECURITY DEFINER` function with an empty search path and an exact `profiles.role = 'admin'` test. Static inspection confirms no direct `profiles` subquery remains in the recreated discovery-brief admin policy.
- **v39:** grants `authenticated` exactly `SELECT`, `INSERT`, and `UPDATE` on `discovery_briefs`, matching its customer policies.
- **v40:** grants `profiles` (`SELECT/INSERT/UPDATE`), `properties` (`SELECT/INSERT/UPDATE/DELETE`), `property_images` (`SELECT/INSERT/UPDATE/DELETE`), `pymes_captacion` (`SELECT/INSERT/UPDATE`), `pymes_diagnosis` (`SELECT/INSERT/UPDATE`), `pymes_plans` (`SELECT`), `tenant_preferences` (`SELECT/INSERT/UPDATE`), `consent_logs` (`SELECT/INSERT`), `forms_dynamic` (`SELECT`), `form_questions` (`SELECT`), and `service_recommendations` (`SELECT`) to `authenticated`.
- **v40 recursion helpers:** customer-data admin policies use `public.is_customer_data_admin()`; form-definition policies use `public.is_forms_admin_or_marketing()`. Both are `SECURITY DEFINER` with an empty search path, and the latter preserves the existing admin/marketing distinction.
- Static inspection confirms the SQL definitions are internally consistent with the operations listed above. This diagnostic did not query Supabase, so it cannot confirm that v38-v40 have actually been applied to the live database or that the live catalog still matches the files.

# Tables/Functions NOT Yet Fixed — needs grants and/or recursion fix

- **`leads`:** directly read with authenticated `SELECT` on every Dashboard, but v38-v40 add no grant. No checked-in customer-own `SELECT` policy exists, so both a grant and an appropriate policy decision would be needed for that count to work. Its admin policy uses the old recursive `profiles` subquery. Lead creation during onboarding itself uses `service_role` and is not blocked by the authenticated grant.
- **`matching_rules`:** tenant profiling performs authenticated `SELECT`. A matching authenticated-read RLS policy exists, but no authenticated table-level `SELECT` grant appears in checked-in migrations. Its admin/marketing policy uses the old recursive `profiles` subquery.
- **`services`:** every Dashboard performs authenticated count-style `SELECT`. A public active-row `SELECT` policy exists, but no authenticated table-level grant appears in checked-in migrations. Its admin policy uses the old recursive `profiles` subquery.
- **`site_content`:** every dashboard layout performs authenticated `SELECT`. A public `SELECT` policy exists, but no authenticated table-level grant appears in checked-in migrations. Its admin policy uses the old recursive `profiles` subquery.
- **`app_config`:** `/dashboard/services` performs authenticated `SELECT` for plan features/timing. A matching authenticated/anonymous read policy exists for those categories, but no authenticated table-level grant appears in checked-in migrations. Its admin policy uses the old recursive `profiles` subquery. The separate Founders-counter read uses `service_role`.
- **`payments`:** `/dashboard/services` performs a count-style `SELECT` for the Founders counter through `service_role`. It is not covered by v38-v40, but no authenticated grant is needed for this specific render-time call. Its checked-in admin policy uses the old recursive `profiles` subquery; customer payment flows outside registration were not traced as part of this journey.
- **`storage.objects` for bucket `property-images`:** Owner and Investor uploads perform Storage `INSERT`; public URL display relies on `SELECT`. Checked-in RLS policies cover authenticated upload and public read, but v38-v40 do not cover this table and its current table privileges were not verified.
- **`public.handle_new_user()`:** invoked as a trigger after Auth signup and writes `profiles`. It was not changed by v38-v40, but it is already `SECURITY DEFINER`, contains no recursive admin check, and is not directly called as an authenticated RPC. No defect is established from static inspection.
- **`public.update_updated_at()`:** invoked by update triggers during owner and tenant profiling. It was not changed by v38-v40, contains no admin-role query, and is not directly called as an authenticated RPC. No defect is established from static inspection.

# Unclear/Needs Human Review (anything ambiguous in the code)

- The initial registration page does not offer distinct Property Owner and Investor Owner roles. Both register as `propietario`; Investor is selected later inside the shared owner form. Whether and where the stored profile becomes `inversionista` is unclear: `profileOwner()` preserves an existing `inversionista` role but does not derive it from the form’s `user_type` value.
- `src/app/results/pymes/[id]/page.tsx` filters `pymes_plans` by `user_id`, but no checked-in migration adds a `user_id` column to that catalog table. The actual live schema must be checked before interpreting this query.
- PYME Path A does not automatically redirect to the main Dashboard; it redirects to a results page whose calls to action point to `/dashboard/services`. Path B shows a success screen and requires a manual **Go to Dashboard** click. Neither path contains a distinct database “activate profile” write.
- Dashboard reads of `leads` conflict with the checked-in RLS model: the code queries a customer’s own lead count, but the table has only admin and service-role policies. This is a code/policy intent ambiguity, not merely a missing-grant diagnosis.
- Current live grants and live policy definitions for all not-yet-covered objects remain unverified because this task explicitly prohibited database access. Statements above about those objects are based only on repository SQL.
