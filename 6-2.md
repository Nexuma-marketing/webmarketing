### #01 — `alexsmarke@gmail.com` says "User already registered" but is not in `/admin/leads` export

**Symptom** (Alex, 2026-06-01)
> "Porque este mail alexsmarke@gmail.com dice que existe, si no aparece en la lista de leads ni la de usuario? aún no se ha limpiado bien la base de datos?"

The signup form rejects `alexsmarke@gmail.com` with the red "User already registered" banner. Yet the leads export (`leads_export_2026-06-01.xlsx`) does not contain that email.

**Root cause**

Supabase splits user state across three tables:

| Table | Stores | Populated by |
|---|---|---|
| `auth.users` | Email + password | `supabase.auth.signUp()` in `/register` |
| `profiles` | Name, role, phone | Trigger on `auth.users` insert |
| `leads` | Marketing pipeline rows | `/api/leads` — called ONLY from inside the form wizards (owner_form, tenant_preferences, pymes_diagnosis), NOT from `/register` |

The "User already registered" check (`supabase.auth.signUp`) reads `auth.users` only. It is unaware of the leads table.

`alexsmarke@gmail.com` exists in `auth.users` because someone registered with it after v32/v33 ran (the cleanup migrations removed the original 20 test rows on 2026-05-22). The new registration never reached the form submit step, so no `/api/leads` call happened and no leads row was created. Result: the email appears registered but is absent from the leads export.

**Verdict**

**Not a code bug. Not a cleanup-migration bug.** Working as designed:
- /register correctly persists to auth.users
- /admin/leads correctly only lists form-completed leads
- The leads export reflects /admin/leads, so it correctly omits register-only accounts

**Action**

No code change. To remove this specific account (if the client wants the email free again):

```sql
DELETE FROM profiles WHERE LOWER(email) = 'alexsmarke@gmail.com';
DELETE FROM auth.users WHERE LOWER(email) = 'alexsmarke@gmail.com';
```

For Alex's understanding, point her at the 3-table model (auth.users vs profiles vs leads).

**Status**: Analyzed — no code change required.

**Update 2026-06-03** — Alex re-reported: *"Pendiente 3 Junio: Sigue igual. Pendiente 1 June: Porque este mail alexsmarke@gmail.com dice que existe, si no aparece en la lista de leads ni la de usuario? aún no se ha limpiado bien la base de datos?"*

The root cause is the same 3-table model explained above, but the most likely current state is now: `auth.users` has the row → signup rejects → but `profiles` row was already deleted (in v32 or by manual cleanup) → so /admin/users also shows nothing. The result is an "orphan" auth.users record that blocks signup but is invisible in both admin panels.

Diagnostic SQL (run to confirm the state):

```sql
SELECT 'auth.users' AS source, id, email, created_at, last_sign_in_at
FROM auth.users WHERE LOWER(email) = 'alexsmarke@gmail.com'
UNION ALL
SELECT 'profiles' AS source, id, email, created_at, NULL
FROM profiles WHERE LOWER(email) = 'alexsmarke@gmail.com';
```

Expected: 1 row from `auth.users` + 0 rows from `profiles` → confirms the orphan state.

Cleanup SQL (run to remove the orphan permanently):

```sql
DELETE FROM auth.users WHERE LOWER(email) = 'alexsmarke@gmail.com';
```

After running, signup with `alexsmarke@gmail.com` will work normally. This is a one-time data cleanup for this specific email — NOT a recurring issue. Every email that ever passes through `/register` creates an auth.users row, so the same situation will recur if anyone tests with an email that later gets manually purged from profiles only.

**Resolution 2026-06-03**

Diagnostic SQL (Tony, 6/3) showed the actual state was different from initially expected:
- `auth.users` had a row created **2026-05-23** (1 day AFTER v33 cleanup of 5/22) — last_sign_in_at 2026-05-27.
- `profiles` ALSO had a row, same UUID `4118b7bf-...`, `full_name = "Prueba property F4"`, `role = "propietario"`.
- 2 payment rows in `/admin/payments` ($200 Low Price + $200 Founder Package) attributed to this profile, both from 2026-05-27.

So `alexsmarke@gmail.com` had been re-registered after v33 by someone (most likely Alex herself during testing — browser autofill of an older form session) and was actively a customer account named "Prueba property F4". Alex didn't recognize it because she was searching `/admin/users` by the *email* but the row is displayed under the *full_name* "Prueba property F4".

Tony ran:

```sql
DELETE FROM profiles WHERE LOWER(email) = 'alexsmarke@gmail.com';
DELETE FROM auth.users WHERE LOWER(email) = 'alexsmarke@gmail.com';
```

Both reported "Success. No rows returned". The email is now fully free. The 2 payment rows remain in `/admin/payments` with `user_id = NULL` (via FK SET NULL) — total revenue still correct, just the customer column shows "Unknown" for those 2 rows. Alex was informed and approved the orphaning of those 2 payment rows in exchange for the email being free.

**Status**: ✅ **Verified 2026-06-03**. SQL cleanup ran successfully. Email now free for re-registration.

2. Renamed the existing `RegisterPage` function body to `RegisterPageContent` — still uses `useSearchParams()`.
3. Added a new `RegisterPage` default export that wraps `RegisterPageContent` in `<Suspense fallback={null}>`.
